# Employee Master

Employee Master defines the company worker/person record; a Frontend User is a separate optional login identity. The canonical identity remains `individuals` / `App\Models\Individual`; no duplicate `employees` table is created. Employee Master operates only on rows where `individuals.type = 'employee'`, preserving customers, vendors, transporters, agents, and master-party rows in the same table.

Task 3.8 adds nullable `employee_code`, `designation`, `factory_id`, and `shift_id` fields to the existing table. Existing values are not backfilled or regenerated. Company scope uses the canonical `company_id`; Department uses the existing `department_id`; Factory and Shift are optional current-state assignments. A factory-scoped Shift must match the Employee Factory; a company-global Shift is valid. Department and Factory combinations are validated against active canonical masters. Employee home Department and Frontend User Department Access are separate concepts.

Employee code is optional because the reviewed live records have no codes. When supplied, it is normalized and unique among non-deleted employees within the company. Names and contact/designation corrections are allowed. Department, Factory, and current/default Shift changes are current-state metadata changes; no transfer or Shift history engine is introduced. Historical operational references to Employee/Individual IDs must never be rewritten when Employee Master changes.

Active and Inactive Employees remain readable historically; inactive employees are excluded from the existing active `/list_employee` operational autocomplete. Referenced employees cannot be hard-deleted; removal is logical and audited. Deactivation does not automatically deactivate a linked Frontend User. Existing `users.individual_id` links are displayed but account creation, passwords, RBAC roles, and User Department Access remain User Management responsibilities. Admin accounts remain on the `admin` guard and are not converted into employee logins.

Employee designation or Department must never be used as a replacement for RBAC authorization. Employee Master is protected by the existing `employees.*` permissions and appears separately from Individuals (All Parties) and User Management under Masters. No payroll, salary, attendance, leave, overtime, biometric, roster, HRMS, customer, vendor, transporter, or authentication redesign is included.
